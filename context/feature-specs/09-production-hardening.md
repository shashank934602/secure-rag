# 09 — Production hardening (Stage B, the parts that need no server)

## Goal

Start the production plan (`docs/production-plan.md`) with the security work that doesn't depend on hosting decisions
(Stage A waits for the owner's answers to D-P1 … D-P3). Close the gates we can close on one machine: **G8** (no secret in
git history, images, or logs), **G10** (per-tenant token budget enforced), and the abuse and identity items of Stage B.
**Done when** CI blocks a commit containing a secret or a dependency with a known critical vulnerability; a user who
floods the API gets 429s; a tenant past its daily token budget gets 429s until the next day; access tokens are RS256 and
expire in 15 minutes; and the tester confirms each.

## Decisions (2026-11-05 — recommended options taken, "build now, study later")

| # | Decision |
|---|----------|
| D1 | **Supply chain in CI** (B4.2–B4.3): `gitleaks` scans every push and, once, the whole history; `pip-audit` checks the locked dependencies against known vulnerabilities; `trivy` scans the built image. A committed secret, any known vulnerability in the locked dependencies, or a high/critical image vulnerability **with a fix available** fails the build; findings with no fix yet don't block. Tools run as pinned images or `uvx`, nothing installed globally. |
| D2 | **Rate limits** (B3.1, ISS-040): fixed one-minute windows, per user (default 20 questions/min) and per tenant (default 120/min), checked after authentication and before anything else runs; over the limit → **429** with `Retry-After`. Counters live in **Redis** (`REDIS_URL`), so several API processes share them; without `REDIS_URL` an in-memory limiter is used (correct for one process: development and tests). |
| D3 | **Daily token budget per tenant** (B3.2, G10): every answered request adds its model tokens (`AnswerResult.usage`, Phase 7) to the tenant's counter for the UTC day; a tenant at or over its budget (default 200,000 tokens/day, the Groq free-tier size) gets **429** until 00:00 UTC. The check happens before any model call; the count after. |
| D4 | **The limiter fails closed** (Invariant 4's spirit): if Redis can't be reached, the request is refused (503), not served unlimited. |
| D5 | **RS256 access tokens, 15 minutes** (B1.1, ISS-047): tokens are signed with a private key and checked with the public key; the algorithm is pinned (no "alg" confusion: an HS256 or `none` token is rejected). Keys are PEM files in `secrets/` (git-ignored), generated by `scripts/make_env.py` with `openssl`; each token carries a key id (`kid`) so keys can be rotated. Default lifetime 15 minutes (`TOKEN_TTL_S`). |
| D6 | **Per-tenant question fingerprints** (ISS-058): `query_hmac = HMAC(HMAC(AUDIT_HMAC_KEY, tenant_id), question)`: the same question no longer matches across tenants. Rows written before this keep their old fingerprints (they stay comparable only among themselves); recorded in the changelog. |
| D7 | **Rate-limited requests aren't audited** (they never reach the answerer), but each writes its JSON log line with `status: "rate_limited"`. |

## Scope limits

- No server, domain, HTTPS proxy, or public exposure: still 127.0.0.1 (Stage A).
- No embedding cache in Redis yet (architecture §10 allows one; not needed at this scale).
- Key rotation is supported by `kid`; the written runbook is part of G9 (later).

## Check when done

- A commit with a fake key pattern fails the gitleaks job; the full-history scan result is recorded.
- 21 quick questions from one user: the 21st is 429 with `Retry-After`; another user is unaffected.
- A tenant whose counter is at its budget gets 429 without any model call; the next UTC day it works.
- Redis stopped → 503, never an unlimited answer.
- An HS256 token, a `none` token, an expired token, and a token signed by another key are all 401.
- All suites green; CI green; the tester's report is in `docs/test-reports/`.
