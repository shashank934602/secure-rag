Issues are about the README not matching what a stranger sees (port clash, API not ready when "Demo ready" prints, cached build time), not about security.

## Findings

**T-1 (medium) The README says to open the page when `seed` prints "Demo ready", but the API is not up for about 3 more minutes.** After "Demo ready" (about +170 s) `/healthz` did not answer until +371 s (api container "health: starting", loading the two local models). A stranger who follows the sentence literally gets connection refused / a blank page and may think it failed. Expected: wording like "when the `api` container reports healthy / the log shows Uvicorn running", or the log line "Demo ready" printed after the API is ready. Evidence: `curl http://127.0.0.1:8002/healthz` failed for about 150 s after the Demo ready line; `docker ps` showed `fresh-clone-api-1 Up 2 minutes (health: starting)`.

**T-2 (medium) The README never mentions `API_PORT` / `DB_PORT`, and the default stack collides with the developer stack.** The README only shows 8000 and 5433; the overrides are in a comment at the top of docker-compose.yml. A reader who already runs `docker compose up -d db` (the README's own Development section, port 5433) or anything on 8000 gets "port is already allocated" when running the Quick start. Suggest one line in Quick start ("port busy? `API_PORT=8001 DB_PORT=5434 docker compose up`") and a note that the page is then on that port. (My brief assumed the README mentions it; it does not.)

**T-3 (low) The "about 10 minutes" claim excludes the first image build, and I could not measure it.** The image is tagged `secure-rag-assistant:local` for any clone (not scoped to the project), so my compose build reused the owner's cached layers and may have re-tagged that name; a first-time build (CPU PyTorch via `uv sync --locked`) is not covered by my 6.5 minutes. Expected: the README states build time (the lesson/changelog do not give one either). Also a shared image name means two checkouts of different commits overwrite each other's `:local` tag. Not measured: a `--no-cache` build, to avoid heavy network use.

**T-4 (low) The page was verified by code reading and a static screenshot only, not by running its JS against a hostile answer.** `app/static/app.js` uses only `textContent` / `replaceChildren` (grep for `innerHTML|insertAdjacent|eval(|document.write` in `app/static/` found nothing), the CSP is `default-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'` plus `nosniff` and `no-referrer` on `/` and `/static/*` (not on `/docs`, as documented), so an answer containing `<img src=x onerror=alert(1)>` would show as literal characters, and inline scripts would be blocked anyway. I did not drive the page in a real browser to type a question, so the in-browser answer view and the 401 message path are not exercised by me (the API side returned 401 for a bad token). Screenshot at 900x1000 renders cleanly: title, token field (password input), question box, four example buttons, Ask, /docs link.

**T-5 (observation) Small things.** (a) The page's example button "What is the hotel limit in London?" is not in the README table; it answers correctly ("£190 per night [expense-policy:1]"). (b) A German question by harriet ("Fasse die Urlaubsregelung zusammen") returned No-Answer (10 s): the corpus is English, consistent with the limits, not a bug. (c) Startup logs include an HF Hub "unauthenticated requests" warning and a torch.jit FutureWarning (noise, no errors; 0 ERROR/Traceback lines in the compose log). (d) The container environment has empty `OPENAI_API_KEY` / `GOOGLE_API_KEY` names from `.env.example`, harmless but unused names. (e) `docker compose run --rm api python -m app.auth token ...` works as written in the README (output is a token line; compose container-status lines appear first on stderr).
