## Findings

**T-1 (medium) gitleaks misses realistic secrets of several kinds.** In a clone I committed 21 fake secrets, using the CI command and the repo's `.gitleaks.toml`. Caught: Groq key (2 forms), Mistral key (`MISTRAL_API_KEY=` form), AWS key pair, PEM private key, JWT, GitHub PAT, Slack token, Hugging Face token (generic rule), OpenAI-style `sk-<48>`, `.env.prod`, `.env.local`, `deploy/.env`. **Missed:** (a) an OpenAI project key `sk-proj-<40>_<40>`; (b) a database URL with a password, `postgresql://postgres:<16 chars>@db.prod.example.com:5432/rag`; (c) our own `JWT_PRIVATE_KEY="<base64 of a PEM, 1600 chars>"` in a non-`.env` file, which is exactly how this project stores its signing key; (d) `prod.env` (the dotenv rule only matches names starting `.env`). The Mistral key is caught only next to the word "mistral" in `KEY = "..."` form, and `Mistral(api_key="...")` was caught only by the generic rule. Why it matters: (c) is the most damaging secret in the system and a copy into a compose override, a CI yml, or a pasted config would pass CI. Suggest a rule for base64 of `-----BEGIN` (`LS0tLS1CRUdJTi`), a `sk-proj-` pattern, a database-URL-with-password rule, and `\.env` anywhere in the file name.

**T-2 (medium) The daily token budget can be overshot by concurrent requests.** Budget set to 1 token; 4 simultaneous `/v1/ask` from alice all returned 200 (the check is before the model call, the count after, as designed in D3). Also one answer can exceed the whole remaining budget, and failed model calls (error path) spend nothing though tokens may have been used. With 20 requests/min/user and 120/min/tenant, a tenant at 199,000 could still run many in-flight answers. The spec's "429 without any model call" holds for sequential requests (verified: second request 429, audit rows unchanged at 49, no model call). Suggest reserving an estimated cost before the call and settling after, or documenting the overshoot bound (rate limit x tokens per answer). Related: a Redis restart (compose runs `--save "" --appendonly no`) resets every tenant's daily count to zero; document it.

**T-3 (low) Stale documentation.** (a) `AGENTS.md` Commands still says "keep 127.0.0.1 until rate limiting, ISS-040" although ISS-040 is closed. (b) `app/main.py` module docstring line 13 says the same. (c) `.env.example` does not list `REDIS_URL`, `RATE_LIMIT_USER_PER_MIN`, `RATE_LIMIT_TENANT_PER_MIN`, `TENANT_DAILY_TOKEN_BUDGET`, `TOKEN_TTL_S` (all are in `app/config.py`). (d) `context/progress-tracker.md` "Current phase" still says v0.8.0 (acceptable until release). (e) `docs/architecture.md` lists Redis as "rate limits + embedding cache", the spec says no embedding cache; fine as a plan. (f) Existing owner `.env` still carries the dead `JWT_SECRET`; `make_env.py` does not mention that it is now unused (CHANGELOG says "no longer used", good).

**T-4 (low) `/healthz` stays "ok" when Redis is down.** With Redis stopped: `/healthz` 200, `/` 200, but every authenticated route 503. The compose healthcheck therefore reports the API healthy while it refuses all traffic. Suggest `/healthz` (or a second readiness check) include a limiter ping. Fail-closed itself is correct: `/v1/audit/verify` 503 and `/v1/ask` 503 with `Retry-After: 30`, no stack trace; after `docker start` the next request worked (403 for alice, expected).

**T-5 (observation) Unauthenticated requests are not rate limited.** 60 no-token and 60 garbage-token requests: all 401, never 429. By design (limit after authentication, D2), but token verification and a DB lookup run for every such request, so an unauthenticated flood is unbounded. Needs the proxy/IP limit of Stage A; worth stating in the spec's scope limits.

**T-6 (observation) Verification does not cap token lifetime.** A token with a valid signature and `exp` one year ahead is accepted (403 on an auditor route = authenticated). The 15 minutes are enforced at issuance only. Matters only if the private key leaks; a `exp - iat <= 900` check would bound a forged-but-signed token. Also `JWT_PREVIOUS_PUBLIC_KEY` rotation was not exercised live (unit tests cover it).

**T-7 (observation) Retry-After is whole seconds, rounded up (up to 1 s early-or-late is possible).** At :20 into the minute it said 40; at :05 it said 55; at :58.4 the 429 would say 2 for 1.6 s remaining. Fine. Budget 429 says 68364 s at about 05:00 UTC, which matches the time to 00:00 UTC (the key's date and the midnight arithmetic both use UTC; reset itself not waited for). The tenant-limit message differs from the user-limit message ("Too many requests from your organisation") and discloses nothing about other users.
