## Findings

**T-1 (medium) The security gate cannot see the guard on/off switches.** `INPUT_GUARD=false uv run python -m eval.gate security` -> `PASSED`, 0 regressions, block rate 0.737. Same for `CONTEXT_GUARD=false`. Expected exit 1 (the guard is off in the app). Cause: `eval.security` builds `InputGuard`/`ContextGuard` directly (eval/security.py lines 191-192) and never reads `settings.input_guard` or `settings.context_guard`; the gate's pins list contains only models. A branch that changes the default in app/config.py to `input_guard: bool = False` (or removes the guard from the graph wiring) passes the security gate. Also not caught: `RERANK=false`, `RERANK_THRESHOLD=-5`, `GROUNDING_JUDGE=false`, `CHUNK_SIZE=800` (all exit 0). Reranker/chunking do not affect the security metrics, so only the first two are real holes, but the grounding judge and output checks are security controls with no gate coverage at all (the quality floors may catch a degraded judge only indirectly). Suggested: add booleans (input_guard, context_guard, grounding_judge) to the pins, and a test that builds the real graph.

**T-2 (medium) A branch can hide regressions by deleting the attack cases.** Reproduced at report level: I took the report from `INJECTION_THRESHOLD=0.9` (gate: FAILED, 9 regressions), removed those 9 attack rows from its `rows`, recomputed the summary with `eval.security.summarise`, and ran `uv run python -m eval.gate security --report .../tampered.json` -> `PASSED`: block rate 0.730 (floor 0.72), context drop 0.533 (floor 0.53), regressions 0. Reason: `case_regressions` (eval/gate.py) skips baseline rows with no counterpart (`if after is not None and ...`), and the datasets come from the branch, not from `main`. So a pull request that weakens a guard and deletes the cases it now fails would pass; `--from-ref` protects thresholds and baseline but not the datasets. A missing baseline attack should be a hard fail (or the dataset files should be read from the ref too, or the count of cases pinned). I did this at report level because I may not edit the datasets; the code path is the same one a dataset edit reaches.

**T-3 (low/medium) Pins compare the current environment, not the report.** A report whose `config` says `chat_model: groq:other` and `rerank: false` run through `gate quality --report` -> `PASSED`. The pin check reads `get_settings()`, so a stale or foreign report is accepted if the machine running the gate is configured correctly. In CI both come from the same run, so the real risk is low; but `--report` is a documented way to run the gate and the pass is not meaningful then. Compare `report["config"]` to the pins too.

**T-4 (medium) Whether a branch can lower its own bar depends on settings the repo does not control.** The workflow reads the bar from `origin/main` on PRs and non-main pushes (good, `--from-ref`). But (a) the gate code (`eval/gate.py`), the dataset files and `.github/workflows/ci.yml` itself are all branch code; a PR can edit the workflow or gate and the PR's own run uses its version; only branch protection with a required reviewer/CODEOWNERS on `eval/`, `.github/`, `eval/thresholds.yaml` closes that (ISS-063 mentions the required check, not CODEOWNERS); (b) on `push` to `main` the bar is the working tree, which is right after review. Documented as a limit in the lesson would be enough.

**T-5 (medium) Secrets reach branch code in the quality job.** `GROQ_API_KEY`/`MISTRAL_API_KEY` are job-level `env`, so every step (including `uv sync` and `uv run` of the branch's code) sees them; a same-repo branch can print or send them. Forks get no secrets on `pull_request`, so the quality job is skipped and reports success (see T-8). Not a flaw for a private single-owner repo; flag for when others can push. Other points checked: `permissions: contents read` (good); no `pull_request_target` (good); the Postgres password in the workflow is a throwaway for a job-only service container (fine); actions pinned to tags (`@v4`, `@v6`), not commit SHAs (low).

**T-6 (low) Quality gate output hides the cost.** `cost_per_query_usd` prints `0.000` in the Markdown diff, although the baseline holds 0.000474 (changelog says $0.00047). Format with more precision for small values. Also the gate HTML for a threshold change shows regressions as `0.726 -> 0.726` (the score did not move; the threshold did) and does not state which config differs from the baseline, so a reader cannot tell why it failed.

**T-7 (low) Unfriendly failures.** `gate quality --report missing.json` and `gate security --report /dev/null` end in a raw Python traceback (`FileNotFoundError`, `JSONDecodeError`); exit code is non-zero (so it still fails closed), but a one-line message is better. `--from-ref nonexistent` gives a clean `no eval/thresholds.yaml at nonexistent`.

**T-8 (observation) Quality-gate skip reads as green.** The job reports success when the secrets are missing or when a PR touches nothing under `app/ eval/ data/ db/`. If it is made a required check, a skipped job counts as passing. Spec D8 lists `app/, eval/, prompts/, data/`; the workflow lists `app|eval|data|db` (there is no top-level `prompts/`; prompts are under `app/prompts` and `eval/prompts`, so covered). The path filter does not include `pyproject.toml`/`uv.lock`/`.github`, so a dependency bump (e.g. a new torch) does not trigger the quality gate. Also `eval.run ... || true` then `grep '^report:'`: if the run crashes before printing the report line, the gate step fails with an argparse-style error rather than a clear "run failed" message.

**T-9 (observation) One lesson claim not reproduced.** Lesson 7 s5: "Only 4 attacks are that close" (borderline). From `eval/baselines/security.json` I count 2 baseline-blocked own attacks with score within 0.05 of 0.5 (a193 0.523, i43 0.545). The definition may include other sets or the other direction; the number should be re-derived or the sentence dropped.

**T-10 (observation) Remaining behaviour.** The gate's targets (block >= 0.95, false refusals <= 0.05) are reported "missed" and do not fail, as ADR-0006 says. Baseline has `judge_unscored: 2` (two golden questions got no correctness score); this is reported but not mentioned in the lesson, and correctness 0.667 is therefore over fewer than 20 scored questions. A first answered request took 57 s (generator 52 s, free-tier backoff while the machine was also running model loads), the earlier 503 took 2.3 s; the 503 body is the documented one. No end-user UI beyond Swagger/ReDoc (observation, as before).
