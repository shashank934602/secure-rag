## Findings

**T-1 (medium) 16 KB body limit bypassed by chunked transfer.** `python3 -c "print('{\"question\":\"'+'a'*3000000+'\"}')" | curl -X POST :8001/v1/ask -H "Authorization: Bearer <alice>" -H 'Content-Type: application/json' -H 'Transfer-Encoding: chunked' --data-binary @-` -> `422` (body fully read and validated). Same for 20 KB and for PATCH acl with a 3 MB body. Expected 413 as with a Content-Length body (which does return `{"detail":"Request body too large"} 413`). Error body no longer echoes input (good), but the memory/bandwidth protection promised in 0.5.1 only covers requests that declare a length. Matters until rate limiting (ISS-040).

**T-2 (medium) A failed request (503) leaves a thin audit record and no log line.** Groq rate limit hit during `/v1/ask`: response `503 {"detail":"The assistant is temporarily unavailable. Try again."}`. Audit: only `request START` (seq 88) and `finish ERROR {"error":"RateLimitError"}` (seq 89); the `input_guard` ALLOW, `retrieve` and `context_guard` decisions already made before the failure are not recorded. The server log has 9 JSON lines for 10 asks: the error request got only `ask failed request_id=... error=RateLimitError`, no `app.requests` line (no latency, no timings). Why it matters: the requests an operator most wants to explain (outages) are the least explained. Row status and `finish` are correct and the query was redacted.

**T-3 (low) Cross-tenant ACL attempt records a foreign document id in the attacker's chain only.** Ned (Northgate) PATCHing Aldermoor's document by uuid gave 403 (by slug it would be 404) and the BLOCK event (seq 7 in Ned's chain) stores the id he supplied. Harmless (his own input); noted because 403 vs 404 differs by role check order: a non-uploader gets 403 even for another tenant's slug (no leak, same as 0.5.0).

**T-4 (low) Not every audited-action attempt is itself audited.** Auditor reads that return 404 (random uuid, and Ned's request id probed by Audrey) and 403 attempts by non-auditors on `/v1/audit/*` produce no `audit_read` event (checked seq between the calls). Spec only requires successful reads; flagging "who tried to look" as a gap for a regulated audience.

**T-5 (low) `context_guard` stage is missing from events when it did nothing; sources hold only top-k.** Spec/changelog list stages request, input_guard, retrieve, context_guard, output_checks, grounding_judge, finish. A normal answer shows request, input_guard, retrieve, output_checks, grounding_judge, finish (seq 37-42); `context_guard` appears only on MASK/DROP. An auditor cannot tell "ran and allowed" from "did not run". Also `output_checks`/`grounding_judge` PASS events have empty details, and `check_citations` appears only in timings.

**T-6 (observation) Cold start benefit not reproduced.** Changelog: first request after restart 14.8 s -> 3.8 s. Measured: server ready 8-11 s after launch (models load at start-up, log shows weights loaded); first request 6.0 s, second 6.3 s (same question type), so no cold-start penalty is visible, but total time is dominated by the free-tier generator (generate 1-12 s, one call 16.5 s). First request in the earlier run was 7.2 s while the test suites ran in parallel.

**T-7 (observation) Detector scope.** NI number `QQ123456C` (invalid prefix) is not masked in `query_redacted` (valid `AB123456C` is). Correct for a checksum/prefix detector, but a user typing a mistyped NI number stores it in clear. Raw text otherwise: `query_redacted` holds the full question when it has no sensitive pattern (by design D4); the same question gives the same `query_hmac` across tenants (key is global), so an admin can correlate across tenants.

**T-8 (observation) Auditor scope.** Northgate has no auditor user, so its audit trail can't be read through the API; the Aldermoor auditor sees none of Northgate's requests (verified, see below). No end-user UI beyond Swagger/ReDoc (`/` is 404).

**T-9 (observation) Over-refusals persist** (ISS-048 area): a 30x repeated benign sentence and the SQL-looking string `'; DROP TABLE audit_events; --` were `refused` at 0.05-0.12 s; a question with IBAN + NI + key + email was refused (classifier BLOCK, redacted in audit). `eval.guards` false refusals b23, b37, b40 unchanged.

**T-10 (observation) Conflicting documents still produce a No-Answer for the payee/reimbursement question** (judge rejected twice, seq 84/86, ISS-019); the audit log explains it, which is the Phase 6 goal.
